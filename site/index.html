fan_out Four drivers, one code path

Four ways in.

A DAG, a CLI, a webhook receiver and a control room. None of them owns a private version of the pipeline — they all end up in the same function.

sandbox Structural security

Credentials never
cross the line.

Security is topology, not a prompt. The orchestrator is the only trusted principal; model-written code runs where it cannot publish.

Trusted Orchestrator

Airflow controls the run.

  • Holds the islo key and the GitHub token
  • Applies and pushes the patch itself
  • Validates paths, scans for secrets
  • Records gates, budgets and metrics
  • GH_TOKEN present the only principal that can push or open a PR
  • MODEL KEY absent the gateway holds it; Airflow never sees it
Format-patch only Hard trust boundary Deny by default
Untrusted Agent sandbox

The agent builds in isolation.

  • A clone, and per-stage allowed tools
  • Native deny rules + a pre-tool hook
  • Bounded turns, time and spend
  • Nothing to push or merge with
  • MODEL KEY phantom swapped for the real one only on egress to the model API
  • GH_TOKEN absent nothing in here can publish anything

The phantom key is never the real one. The gateway swaps it in only on egress to the model API. And delivery runs backwards: deliver pulls a git format-patch stream out of the sandbox, validates it, then applies and pushes it from the orchestrator. A hit is a policy error and nothing is published — so “the agent never pushes or merges” is structural.

  • no .. path escapes
  • no symlink modes
  • no .git/ writes
  • no secret-shaped tokens

blueprint Factory as code

Change the line,
not the engine.

blueprints/<name>.toml declares the stage order, the human gates, the limits, the target repos, the sandbox profile and the PR labels. dags/blueprints.py reads every file with stdlib tomllib at DAG parse time and emits one Airflow DAG per blueprint. The unit of deployment is the file.

  • Jobs = issues × targets, via dynamic task mapping
  • One mapped task group per job, with its own sandbox and approvals
  • default → DAG factory: 6 stages, 2 gates
  • hotfix → 5 stages, no spec, self-approving intent gate
blueprints/default.toml 
[blueprint]
name = "factory"

[[targets]]
repo = "zozo123/ariflow-swfactory"
dir = "demo/target"
base_branch = "main"

[stages]
order = [
  "intent", "spec", "plan",
  "build_and_test", "review", "deliver",
]

[[gates]]
after = "intent"
artifact = "intent.md"
timeout_h = 24

[[gates]]
after = "plan"
artifact = "plan.md"
timeout_h = 24

[limits]
max_build_iterations = 3
budget_usd_per_stage = 2.0
budget_usd = 8.0
max_parallel_jobs = 4

[sandbox]
kind = "islo"

[deliver]
labels = ["factory", "agent-authored"]

metrics The loop closes

Every run tunes
the next one.

Per-run metrics feed bands.yaml: mean and standard deviation over a 20-run window, three response tiers, and only the tiers that say so involve the model. Scripted demo runs are ignored, so they never move the bands.

  1. 1σ log record the breach and move on
  2. 2σ diagnose read-only agent writes an incident record and opens an issue
  3. 3σ propose it drafts an intent and files it labeled factory — back into the factory
